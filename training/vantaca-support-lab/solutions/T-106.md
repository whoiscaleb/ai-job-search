# T-106 solution · Late-fee job is not idempotent

**Root cause:** `usp_ApplyLateFees` charges a fee on every unpaid assessment past its grace period. It never checks whether a fee was **already** charged for that assessment. The job ran on 9/12 (correct) and again on 10/12, and the second run re-charged September.

**How you'd find it:**
```sql
SELECT RelatedChargeId, COUNT(*) AS FeeCount
FROM dbo.Charges
WHERE ChargeType = 'LateFee'
GROUP BY RelatedChargeId
HAVING COUNT(*) > 1;           -- charges 23 (A2) and 29 (B1): 2 fees each
```
Running `latefees 2 2026-10-15` creates **4 more** fees, which proves the job isn't safe to re-run.

**Procedure fix:** add one condition to the WHERE clause:
```sql
      AND NOT EXISTS (SELECT 1 FROM dbo.Charges lf
                      WHERE lf.ChargeType = 'LateFee'
                        AND lf.RelatedChargeId = c.ChargeId)
```
Verified: after the fix and the data cleanup, re-running for Lakeview creates 0 fees. Running Pine Ridge twice creates 4, then 0.

**Data fix:**
```sql
-- 1. Identify duplicates (keep the first fee per assessment)
WITH Ranked AS (
    SELECT ChargeId,
           ROW_NUMBER() OVER (PARTITION BY RelatedChargeId ORDER BY CreatedAt, ChargeId) AS rn
    FROM dbo.Charges
    WHERE ChargeType = 'LateFee'
)
SELECT c.ChargeId, c.UnitId, c.Description, c.Amount, c.CreatedAt
FROM dbo.Charges c JOIN Ranked r ON r.ChargeId = c.ChargeId
WHERE r.rn > 1;                                  -- expect ChargeId 33 and 35, $50 each

-- 2. Make sure nobody paid against them (a delete would orphan the payment)
SELECT * FROM dbo.PaymentApplications WHERE ChargeId IN (33, 35);   -- expect 0 rows

-- 3. Delete inside a transaction
BEGIN TRAN;

WITH Ranked AS (
    SELECT ChargeId,
           ROW_NUMBER() OVER (PARTITION BY RelatedChargeId ORDER BY CreatedAt, ChargeId) AS rn
    FROM dbo.Charges
    WHERE ChargeType = 'LateFee'
)
DELETE c
FROM dbo.Charges c JOIN Ranked r ON r.ChargeId = c.ChargeId
WHERE r.rn > 1;

SELECT @@ROWCOUNT AS RowsDeleted;                -- must be exactly 2

-- COMMIT;   -- only after the count matches step 1
-- ROLLBACK;
```
In real accounting software you'd often **reverse** a charge with a credit entry instead of deleting it, so the audit trail stays intact. Ask your lead what Vantaca's standard is before deleting financial records.
